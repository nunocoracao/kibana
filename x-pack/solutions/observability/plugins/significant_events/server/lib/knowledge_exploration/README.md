# Unified Nightshift Detection Agent

This branch replaces the staged detection workflow with one autonomous tool loop. It ports the exploration, monitoring and event capabilities from `nuno/ki-extraction-agent-improvements` into one shared run, evidence session, prompt, lease, history and cost ledger. `problem_prompt.text` is the only system prompt. Direct current telemetry can establish a significant event before a rule fires or a full KI extraction phase runs. Inspectable signals and a verified affected-service KI anchor are required; the writer resolves existing anchors or requests the minimal verified identity first. The same agent also persists useful learned facts and validated measurements and evaluates ongoing native monitoring coverage during healthy operation. A healthy run cannot silently skip monitoring assessment when current telemetry and budget are available; there is no minimum artifact count. Quiet historical namespaces are recorded as gaps rather than repeatedly blocking progress on the active estate.

## Run and control

Open **Nightshift → Detections → Agent Explorer** (`/app/nightshift/detections/agent`; local dev adds `/dev`). Add an enabled source first, then choose a model and Run now. Adding or changing a source does not launch an extraction workflow. Source edits cancel the current run and reconcile catalog ownership.

The panel provides Run/Stop, model selection, schedule toggle, frequency in minutes, run traces, tool input/output inspection, prompt/tool anatomy, cumulative cost and duration, history, and confirmed resets. Scheduling is off by default. It uses a persistent Task Manager task with the scheduling user's credentials and a per-space run lease; it survives Kibana restarts and does not overlap a manual run. Global pause blocks new runs and cancels the current local run. Native monitoring rules execute independently of the agent schedule.

The management API is `/internal/significant_events/problem_agent`: GET status, GET `/anatomy`, POST `/_run` (optional `{ "evaluationMode": true }` for an explicitly unbounded test invocation), POST `/_cancel`, GET `/runs/{runId}`, PUT `/model` and PUT `/settings` (`enabled`, optional `intervalMinutes`, 1–10080). Manage/configure privileges, supported-space checks and feature/license access apply. The local mock SAML role picker remains the login flow; the prototype adds no user/password setup.

## Evidence and ownership

Every invocation reviews existing active problems and checks new current outcomes across enabled configured sources. Queries use explicit bounded windows, observed ECS/OTel fields, source and namespace scope, and run-local evidence references. Event writes require fresh evidence for every confirming source, within three minutes and without a historical end offset. A run cannot complete an assessment while leaving its initial active problems unchecked; it must report partial with the outstanding IDs.

Stable `nightshift-problem-<issueKey>` IDs preserve continuation, recovery and recurrence. The native event client provides optimistic updates and episode behavior; operator dismissals are honored. Native events retain actual executed source-query signals (`type=query`), observed rows, fixed evidence windows and affected source-local service KIs. Open in Discover preserves the executed query including its aggregates/projections. Query signals never fabricate a detection or a rule firing; validated native query/rule references are attached separately. The event flyout and chat canvas expose this evidence, affected entities and supported causal features. Reviews enrich earlier disconnected records with current evidence and can recover original evidence from an available original run trace. Cleared history cannot supply missing historical proof. Assessment notes also identify the current run. Recovery requires positive healthy operation outcomes or clearance of every confirming mechanism. Missing telemetry, empty fired-rule lists and a successful fault revert are not recovery evidence.

Knowledge writes preserve logical KI identity and source provenance. New agent-owned features carry `meta.problem_agent_owner`; standalone query KIs carry an ownership evidence marker. Existing user KIs retain ownership when enriched. Standalone query writes use canonical KI bulk storage without invoking the retired query-promotion orchestrator; they cannot overwrite a rule-backed query reference. Metric monitor pipelines must group by bucket=BUCKET(@timestamp,1 minute) after STATS BY; baseline, validation and native execution all retain that complete-minute bucket contract. Monitoring uses native signal rules with `nightshift:agent:problem-agent` ownership and stable intent IDs. Actual query validation, positive witnesses/non-null instruments, service AND namespace boundaries, equivalent-query reuse, and the seven-active-rule cap per emitting service/namespace across sources remain in place. User rules are context, never mutable through these tools.

Reset outputs stops the run and removes this agent's knowledge, native monitors and problem-event versions in the current space. It preserves configured sources, user-owned knowledge/rules, run traces and cost totals. Reset history removes traces and displayed totals while preserving outputs; reset totals only clears displayed accounting. Bulk operations require explicit literal confirmations. Incurred provider charges cannot be reset.

Legacy detection workflows are retired through their managed owner reconciliation. Source onboarding, continuous extraction, query generation and discovery execution routes reject legacy starts; read contracts remain for compatibility. Investigation workflows are independent. The existing event/rule/knowledge views read native records.

## Learning across runs

Reusable detection/recovery lessons use ordinary native KIs (`type=schema`, `subtype=custom`, `properties.kind=detection_learning`). They retain supported failure signatures, positive recovery tests, benign lookalikes, actual saved query/rule references and precise unknowns/revisit triggers. The prompt asks for stable, revisable lessons after useful event assessments, without inventing causes or rewriting a lesson merely because another healthy run succeeded. A bounded selection of applicable lessons from enabled sources is loaded into each invocation; excluded/expired knowledge is omitted. These records appear in the existing Knowledge UI and survive clearing run history. Resetting owned outputs removes them with the other owned KIs.

The first model step exposes its starting lessons, recent feedback and unresolved work for inspection in Agent Explorer. The existing per-space state carries the latest three bounded run summaries, read counts, durations, costs and tool failures for planning. Current telemetry still determines every event decision. Explicit knowledge gaps survive a run that completed its current-health coverage, and can be cleared explicitly when resolved. After urgent current problems, the agent can spend remaining budget on unknown entities, directed relationships, unparsed operations, recovery tests and useful monitor coverage. There is no extra agent, staged pipeline or artifact quota, and no claim that latency/cost has improved without a controlled comparison.

Knowledge JSON batches validate records independently. A query object accidentally mixed into `featuresJson` is routed through the existing standalone query writer. Valid feature/query records persist while malformed records return compact ID/field rejections and a truthful partial result. Queries still require source-scoped STATS and cannot overwrite rule-backed references. Finish input bounds match runtime limits, and an explicit `monitoringBlocker` lets the agent record a genuine data/query gap without manufacturing a monitor. Learning feedback identifies actually observed source-local entity gaps. Event creation/status transitions require a reusable native detection-learning record, unless persistence is genuinely blocked. Canonical shared severity and confidence contracts are included in the system instructions and event tool rather than replaced by a separate scoring system.

## Throughput and estate coverage

Every source's first data query requires a capped one-minute volume/latency probe before execution; the tool returns planning feedback and leaves the requested query unexecuted until the agent can choose scope. Capped volume is a lower bound. `LIMIT` does not bound scanned work. `sampleProbability` adds ES|QL probability sampling after explicit time/service/namespace scope for exploratory custom/sample/relationship reads. Counts are labelled approximate; sampled-only reads cannot confirm active/recovery writes. CATEGORIZE groups representative patterns and is not itself a scan limit. Confirmation uses exact small scoped windows. Partial query results cannot become evidence.

Explicit sample pipelines are executed as custom reads rather than silently ignored. Category rows expose age of their last observation, and combined reads warn when requested services are absent from the page. Fractional sampling probabilities pass the same JSON-schema adapter used by inference.

A bounded current emitting-service inventory accompanies each source's first data read, including narrow incident reads. Identity aliases are coalesced and rare services are visible. The inventory reports truncation; it is not a health check. Custom queries now honor offset pagination. Finish feedback distinguishes substantive outcome coverage, representative payload inspection for unfamiliar log emitters, native knowledge persistence and useful monitoring assessment. Existing source-local payload contracts can be reused. Unassessed emitting services remain explicit gaps, so lifecycle checks cannot silently claim estate-wide completeness. Available current checks continue while budget/data permit; true source access/timeout blockers and normal execution budgets still allow honest partial exits. A completed empty scoped read is an explicit unknown and keeps coverage partial; an emitter aging out of the initial inventory window must not cause an infinite finish loop. Single-service query scope can establish assessment identity without changing the stored result rows. These feedback checks guide real progress without requiring fabricated incidents or rule counts. Repeated identical unresolved feedback stops explicitly partial rather than consuming unlimited budget without progress; source title/type stay visible. Historical comparison windows are contextual signals, rather than current confirmations/refutations. New keys that overlap previously indexed affected entities require identity review or an explicit explanation of an independent mechanism; this prevents narrower attribution alone from silently creating a new incident.

## Limits and accounting

The default connector is GPT-6 Luna Pro; any available priced connector can be selected. Each run snapshots actual connector/model, limits and Elastic catalog prices. Learning focus: 20 minutes/96 turns/5.12M cumulative reported tokens. Established operation focus: 10 minutes/48 turns/2.56M cumulative tokens. Both have a $50 estimated chat ceiling, not a spending target. Model requests have a 180-second deadline, bounded retries and cancellation. Missing/unpriceable usage stops cost-protected work and is marked incomplete; abandoned requests can still be billed. Estimates exclude embeddings, cache-write costs and Elasticsearch compute. The cumulative warning can remain after a later fully priced run because earlier timed-out, interrupted or cancelled requests never returned usage; affected runs are marked with an asterisk. Retried model steps retain the timeout warning after the retry succeeds. Model responses are collected as inference events so reported token usage survives a tool-argument validation failure; rejected batches execute nothing and return the exact validation feedback to the agent within the existing turn/cost limits. If usage is absent, cost-protected execution stops. Missing provider usage is not replaced with a fabricated estimate. An explicit manual `POST /_run` body `{ "evaluationMode": true }` snapshots null duration, turn, cumulative-token and estimated-cost limits for that invocation only. It also permits continuing through unreported usage while marking estimates incomplete. Normal manual/UI/scheduled runs retain their defaults. Per-request deadlines/retries and tool timeouts remain operational failure handling; they are not total-run budgets. Evaluation mode remains cancellable and uses the same per-space lease and permissions.

Run state and traces use space-scoped saved objects, CAS writes, leases and heartbeats. Interrupted runs retain prior writes and concrete unfinished work. Learning focus is selected from persisted source-scoped knowledge, measurements and monitoring associations. Missing foundations, uncovered known emitting services or a new source return effort to learning; resetting cost/history counters does not determine readiness. These are minimum inventory signals, not a proof of useful coverage or a rule-count target. Current active problems take priority in either mode. The older internal exploration names are retained to reuse the proven storage, sampling and trace components; there is one instantiated problem-agent service.
