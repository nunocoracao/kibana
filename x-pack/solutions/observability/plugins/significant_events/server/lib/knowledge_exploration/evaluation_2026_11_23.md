# Detection Agent CARL quality campaign — 2026-11-23

This campaign ran 27 invocations (21 completed and 6 development cancellations) and 13 fault injections across six dungeons. It improved rare-failure assessment, currentness, incident evidence and recovery. It also retained important misses: early low-rate failures were dismissed, latency regressions were compared with already-degraded baselines, and uniform sampling hid sparse errors. Developed retests are reported separately from those failures. This is an adaptive prototype evaluation, not an independent benchmark or a detection-latency SLA.

Work took place in `kibana-fork`, branch `one_agent_to_rule_them_all`. The existing three logs/metrics/traces sources were preserved. The target received configured source metadata, stored knowledge/measurements/rules/events and indexed telemetry. It never received Carl's topology, fault handles, expected results or observer queries. No dungeon-specific conditions were added to the agent implementation.

## General improvements

- Current outcomes and recovery precede background learning. Historical reads and probability samples no longer satisfy exact current-emitter coverage. After lengthy learning, a bounded refresh revisits stale scopes; it does not chase an endless moving three-minute horizon. Aged observations and unavailable populations stay explicit partials, with collection times preserved.
- Uniform sampling is appropriate for dense exploration, not ruling out rare failures. Guidance separates scoped exact terminal-outcome counts from sampled payload/latency exploration. Preserve meaningful cohorts, successes, expected rejections and unknowns. `LIMIT` and `CATEGORIZE` do not cap source scans. No universal error-rate or minimum-count threshold was introduced.
- A continuing problem cannot become its own healthy baseline. Duration guidance uses actual fields/units, progressively broader sampled history when needed, matched populations and exact small-window confirmation. Sparse-failure guidance distinguishes an established tolerated background from two neighboring degraded windows. Successful unrelated operations do not cancel failed attempts.
- Known duration contracts receive completion feedback when useful measurements/comparisons were skipped. Null or empty scoped aggregates can yield an explicit data/parsing gap without indefinite equivalent queries. This is heuristic coverage feedback, not proof that all instruments or SLOs were understood.
- Native events retain executed fixed-window query signals and actual affected-service anchors. Rows explicitly identifying a different service are context, not confirmation. Titles can improve as diagnoses/recovery change. Existing valid query/native-rule references survive updates; an unbacked query's generated ID is not treated as an installed rule.
- Evidence validation identifies the selected source, rejected refs, read ages and query windows. It asks for a new short exact read rather than vaguely demanding every source. Literal dotted JSON keys require bracket JSONPath; all-null dotted-path queries receive actionable advice.
- Learned detection/recovery signatures, benign lookalikes, baseline provenance, reusable queries and native monitors stay in the existing stores and UI contracts. No replacement workflow, artificial seeded incidents or simulator-specific detector was added.

## Evaluation method and limits

Every target invocation used `evaluationMode=true` with null total duration, turn, token and estimated-cost ceilings. Per-request operational deadlines, cancellation and repeated-no-progress handling remain. Development cancellations are retained with their reasons: a stale activation, a sampled rare-failure miss, a rolling-refresh liveness failure, and data-gap/no-progress bookkeeping after native recovery writes had already succeeded. They are not successful completed controls.

Luna Pro, Sol and Astra were exercised. Workloads, prompt/tool versions and stored knowledge changed sequentially; these are not controlled model rankings. The original model was retested after development; the final model selection and retained schedule settings are recorded below. All timing is UTC. Detection timing separates injection, actual emitted impact and manual invocation; these tests do not measure Task Manager scheduling delay.

The `nightshift-evals` repository supplied output-only KI checks and attribution ideas; `nightshift-agent-eval` supplied evidence/impact/recovery scoring ideas. Their destructive setup/replay runners were not used on this stack. Adapted KI checks are not official task accuracy scores: source views, native subtype extensions and namespace partitioning differ from legacy assumptions. The first KI metric snapshot was collected during development, not before the initial run. Exact-ID duplicates do not measure semantic duplication. No universal precision/recall or statistically calibrated confidence is claimed.

Native history independently confirmed minute-scheduled executions of the newly saved latency monitor. That proves execution, not sensitivity to every future shift or a fabricated firing. Some model prose still overstates window completeness or significance; executed rows and native versions remain the evidence of record. Fixed query windows preserve collection times, but late ingestion can change a later rerun’s rows. Further evaluation should emphasize unseen sparse cohorts, stable successful fallback controls, denominator consistency and broad metrics/traces semantics.

The compact machine ledger contains run IDs, prompt hashes, actual limits, estimates/completeness, tool errors, event write outcomes, fault handles/times, native lifecycle snapshots and capture IDs. Raw local artifacts remain in `/private/tmp/nightshift-quality-20261123/`; authenticated helper files there are not part of the committed report.
