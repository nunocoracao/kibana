# Manage an event

For a fresh problem, query events with action=index, includeInactive=true, sourceIds and the affected entity KIs in featureIds. Compare prior records by operation, cohort and failure mechanism. Wording may change. Pass the matching eventId for recurrence, including after four hours so the tool can start a new occurrence. For a distinct mechanism choose a stable lowercase issueKey from the operation and symptom. Omit timestamps and run IDs; the tool versions recurring episodes. Keep unrelated inactive history out of routine scans.

Write the verified symptom promptly. Cite current executed evidenceRefs for each source. Identify actually affected entities and the time window. Include numerator, denominator, baseline, blast radius and unknowns; attach actual ruleIds and firing signalRefs when available. Query signals can support a finding before a rule exists. Give the cause only when directed evidence supports it. Rate severity from verified impact, and confidence from strength and independence of evidence. Use status=active for ongoing harm.

Before opening a second event from trailing failures, check whether the same requests belong to an existing episode. When the order within a minute is ambiguous, query first and last timestamps for failed and successful starts and completions. Before opening a new active event require evidence that newly arriving work is affected. If only earlier starts failed and succeeding new starts extend beyond the last affected start, attribute the failures to the earlier episode. Unknown recovery of historical work alone warrants a follow-up check.

On review, name the operation in openingCondition, then measure that operation first. If its excess has cleared and it is completing successfully, close that event. A related service with a different terminal outcome requires its own current impact assessment. Preserve the original event identity and scope through closing.

When downstream failures complete after the original path recovers, run a custom source query before calling events. With a verified millisecond duration on completion records use EVAL started=TO_DATETIME(TO_LONG(@timestamp)-TO_LONG(elapsed_ms)). For successes and failures return COUNT(*), MIN(started), MAX(started) and MAX(@timestamp) by outcome. Otherwise join the timeline by request IDs or inspect explicit start records. A historical failure completing now cannot keep a recovered caller operation active. If timing or units are unavailable, report uncertainty on the downstream service independently. Group residual failures by reason or dependency. Show successful outcomes after the last incident-specific failure and enough observations for its previous frequency. A quiet signal or absent traffic leaves recovery unverified. If the excess clears, upsert status=inactive with fresh evidence and an assessmentNote. Preserve episode severity. Correct a false positive when the original episode itself matches ordinary behavior. Respect operator dismissal. Record the reusable opening and recovery measurements.
