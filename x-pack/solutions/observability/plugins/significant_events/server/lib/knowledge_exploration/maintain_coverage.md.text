# Learn the system and maintain monitoring

On a new system, save verified service and dependency KIs and a few reusable operation measurements. Start with narrow KI indexes, follow cursors and fetch details by logical ID. For a service entity put the observed emitter in properties.name and its namespace in properties.service_namespace. Group writes by observing source. Set top-level sourceId on each upsert and use evidence_refs from that source. After a transition, use a stable schema/custom KI with properties.kind="detection_learning", properties.event_id set to the returned event ID, and evidence_refs. Include the detection and recovery conditions, ordinary lookalikes, and remaining uncertainty.

On a cold source, persist a small batch of observed emitter or workload KIs as soon as you have evidence. Inspect bounded peers and relationship samples for an explicitly named destination, caller and operation. Save edges with evidence of who calls whom. Use field names and aggregate counts for sensitive telemetry; keep payload secrets and personal values out of examples. An inconclusive incident or monitor does not invalidate those observations. Choose a recurring operation with observable terminal outcomes. For an error-signature rule, verify a positive witness and ordinary traffic. For preventive coverage on a healthy system, use a native metric rule for a meaningful, observed operation measure such as duration, timeout share or backlog. Validate the units, grouping, population and finite values over comparable buckets. A healthy zero in an observed failure-share series is useful. Install the validated measurement; an actual prior incident is unnecessary for that kind of rule. Distinguish an operational rule from a stats query saved on a KI. For an uncovered problem, start with the executed source_esql query that distinguished the affected cohort. Inspect monitoring_inventory for the same source, operation and failure condition. A rule for a different error on the same service leaves this gap open.

1. Inspect a raw positive example and a normal example. Keep every column used by the predicate, including each COALESCE argument. Use the emitter fields actually present on the positive row and compare values with literals of the mapped type. If parsing JSON, project the extracted values with EVAL and verify them in actual rows. A literal dotted key such as error.code requires JSON_EXTRACT(message, "['error.code']"). A nested object uses a dotted path. Inspect field types and units.
2. Reuse the measured pipeline after FROM. Remove absolute time filters, terminal KEEP/LIMIT and sorting intended for display. For count monitors use WHERE predicates with positiveEvidenceRefs. Inline extraction in WHERE, e.g. WHERE JSON_EXTRACT(message, "outcome") == "failed". A read-only count baseline can use EVAL before WHERE. For installation, inline the expression or keep EVAL and add an explicit metric aggregation. For ratios or latency, emit a numeric metric_value grouped by bucket=BUCKET(@timestamp, 1 minute) and the affected dimensions. Preserve ordinary traffic and genuine zeroes. For a share, use floating-point arithmetic. Establish what the metric measures in both the affected and ordinary windows.
3. Supply the pipeline to monitoring_rules baseline or validate. For an installed rule, validate by ruleId. For a new rule, use the source's actual featureIds. Inspect returned rows. A syntax error, omitted column or missing argument can be repaired from the example. Retry with the corrected predicate. Keep a detector scoped to the proven symptom; a broad failure metric can include business rejections.
4. Upsert justified coverage using the returned validationRef, stable slug, title, description, reason and featureIds. Link the returned ID to an active event. For an already recovered incident include its detection_learning KI in the rule's featureIds. Verify native ownership and reuse equivalent rules. If the specific issue cannot be monitored reliably, record the actual validation or data obstacle under eventMonitoringBlockers. Continue monitoring other observable operations.
